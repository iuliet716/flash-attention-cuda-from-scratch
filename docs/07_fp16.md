# Step 07. Half-Precision (FP16)

## What this step implements

Step 06 optimized the shared-memory layout, but Q, K, V, and O were still stored in FP32.

This step changes the fused attention kernel to **FP16 inputs, Q/K/V shared-memory tiles, and output** while keeping numerically sensitive accumulation in FP32.

```text
Q, K, V storage       : FP16
Q/K/V shared tiles    : FP16
QK^T accumulation     : FP32
online softmax        : FP32
PV accumulation       : FP32
O storage             : FP16
```

This reduces the amount of data moved through global and shared memory and prepares the kernel for Tensor Core operations in the next step.

The arithmetic path itself is unchanged in Step 07: $QK^\top$ and $PV$ still use conventional FP32 multiply-add operations, and no Tensor Cores are used.

## FP16 data path

The kernel now operates on CUDA `__half` values:

```cuda
__global__ void fused_attention_kernel(
    const __half* __restrict__ Q,
    const __half* __restrict__ K,
    const __half* __restrict__ V,
    __half* __restrict__ O,
    int N,
    int d,
    float scale)
```

Shared-memory tiles also change from `float` to `__half`:

```cuda
extern __shared__ __align__(16) __half smem[];

__half* Qtile = smem;
__half* Ktile = Qtile + BR * d;
__half* Vtile = Ktile + BC * d;
```

Therefore, the same Q/K/V tiles require half the shared-memory capacity compared with FP32.

```text
Step 06

Q tile : BR x d x 4 bytes
K tile : BC x d x 4 bytes
V tile : BC x d x 4 bytes

Step 07

Q tile : BR x d x 2 bytes
K tile : BC x d x 2 bytes
V tile : BC x d x 2 bytes
```

The tiling strategy and the K-tile swizzle remain unchanged.

## 16-byte vectorized loads

Step 05 introduced `float4` as a 16-byte vectorized memory transaction.

The same 16-byte access is retained in this step, but the underlying data is now FP16.

```cuda
const int d8 = d / 8;

const float4* Qb4 = reinterpret_cast<const float4*>(Qb);
float4* Qtile4 = reinterpret_cast<float4*>(Qtile);
```

Here, `float4` is used only as an aligned 16-byte transport type. The values stored in the chunk remain FP16.

A 16-byte chunk now contains:

```text
FP32 : 4 values x 4 bytes = 16 bytes
FP16 : 8 values x 2 bytes = 16 bytes
```

So each vectorized load moves **eight FP16 values** instead of four FP32 values.

For example, the Q tile is loaded as:

```cuda
for (int idx = threadIdx.x; idx < BR * d8; idx += blockDim.x) {
    const int r = q_base + idx / d8;

    if (r < N) Qtile4[idx] = Qb4[(size_t)r * d8 + idx % d8];
}
```

The K and V tiles use the same 16-byte access size, while K retains the XOR-swizzled shared-memory layout from Step 06.

## Alignment and head-dimension constraint

The shared-memory region remains explicitly 16-byte aligned for `float4` access:

```cuda
extern __shared__ __align__(16) __half smem[];
```

The host wrapper enforces:

```cpp
TORCH_CHECK(
    d <= FUSED_D_MAX,
    "head dim must be <= ", FUSED_D_MAX, ", got ", d
);

TORCH_CHECK(
    d % 64 == 0,
    "head dim must be a multiple of 64, got ", d
);
```

Each vector chunk contains eight halves, so one row contains `d / 8` chunks.  
The XOR swizzle uses `r % 8`; requiring `d / 8` to be a multiple of eight keeps the permuted chunk index inside the same row.

With `FUSED_D_MAX = 128`, this implementation supports the benchmarked head dimensions `d = 64` and `d = 128`.

## FP32 dot-product accumulation

Although Q and K are stored as FP16, the $QK^\top$ dot product is still accumulated in FP32.

Each 16-byte chunk contains eight half values.  
They are interpreted as four `__half2` pairs and converted to FP32 before multiplication:

```cuda
const float4 a = q8[c];
const float4 b = k8[swizzle(lane, c)];

const __half2* ah = reinterpret_cast<const __half2*>(&a);
const __half2* bh = reinterpret_cast<const __half2*>(&b);

for (int j = 0; j < 4; ++j) {
    const float2 qf = __half22float2(ah[j]);
    const float2 kf = __half22float2(bh[j]);

    dot += qf.x * kf.x
         + qf.y * kf.y;
}
```

Here, `dot` remains an FP32 accumulator:

```cuda
float dot = 0.0f;
```

Therefore, this step reduces operand storage precision without changing the dot-product accumulation precision.

## FP32 online softmax and output accumulation

The online-softmax state also remains FP32:

```cuda
float m = -FLT_MAX;
float l = 0.0f;
float acc[ACC];
```

The running maximum, normalization factor, and output accumulator are therefore not stored in FP16.

During $PV$, V is converted to FP32 before accumulation:

```cuda
acc[i] += pc * __half2float(
    Vtile[c * d + k]
);
```

Only the final normalized output is converted back to FP16:

```cuda
Ob[(size_t)row * d + k] =
    __float2half(acc[i] * inv_l);
```

This keeps the numerically sensitive reductions and accumulations in FP32 while reducing the storage and memory-transfer cost of Q, K, V, and O.

This is a mixed-precision kernel rather than a pure-FP16 arithmetic kernel.  
It is also not numerically identical to Step 06 because the inputs and final output are rounded to FP16.

| Global-load sectors | 4.30B | 2.15B |

| Issue-active cycles | 50.0% | 67.1% |

FP16 storage halves global-load requests and sectors because each 16-byte access now carries eight values instead of four.

Shared-load wavefronts also decrease by 30.0%, accompanied by lower MIO stalls and more eligible warps.

The smaller shared-memory footprint does not increase occupancy in this profile:
registers still limit residency to four blocks per SM.

## Conclusion

Step 07 changes Q/K/V/O storage to FP16 while retaining FP32 accumulation,
reducing memory traffic and MIO pressure.

The kernel remains limited by the on-chip memory path, with residual shared-store conflicts.  
The matrix operations still use scalar FP32 arithmetic, and Tensor-pipe utilization remains 0%.

Step 08 introduces WMMA Tensor Core operations for $QK^\top$.
