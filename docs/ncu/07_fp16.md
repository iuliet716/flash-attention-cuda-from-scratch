# Nsight Compute Analysis — Step 07: Half-Precision (FP16)

This document contains the detailed Nsight Compute analysis for [Step 07: Half-Precision (FP16)](../07_fp16.md).

The goal is to measure how FP16 storage changes memory traffic and scheduler efficiency while retaining FP32 accumulation.

## Profiling setup

Representative workload:

```text
GPU: NVIDIA GeForce RTX 5090
dtype: FP16 storage with FP32 accumulation

B = 8
H = 16
N = 4096
d = 64
```

The attention algorithm, tile sizes, thread mapping, and K-tile XOR swizzle are retained from Step 06.

Q/K/V/O storage and Q/K/V shared-memory tiles change to FP16.  
Dot products, online softmax, and output accumulation remain FP32.

## Overview

| Metric | Step 06 FP32 | Step 07 FP16 |
| --- | ---: | ---: |
| SM Throughput | 93.4% | 94.3% |
| L1/TEX Throughput | 93.5% | 94.3% |
| L2 Throughput | 27.9% | 15.6% |
| DRAM Throughput | 0.45% | 0.31% |
| Global-load requests | 268.70M | 134.35M |
| Global-load sectors | 4.30B | 2.15B |
| Shared-load requests | 6.44B | 5.37B |
| Shared-load wavefronts | 10.74B | 7.52B |
| MIO-throttle stall / issued inst. | 6.77 cycles | 3.69 cycles |
| Warp cycles / issued inst. | 15.96 cycles | 11.89 cycles |
| Eligible warps / scheduler | 1.51 | 2.26 |
| Issue-active cycles | 50.0% | 67.1% |
| Achieved occupancy | 66.5% | 66.5% |

FP16 storage reduces memory requests and wavefronts.  
Lower MIO stalls accompany improved instruction issue at the same occupancy.

## Reduced memory traffic

The vector access width remains 16 bytes:

| Storage type | Values per 16-byte access |
| --- | ---: |
| FP32 | 4 |
| FP16 | 8 |

Each access carries twice as many values, halving global-load requests and sectors.

Global-store requests remain unchanged because the output uses the same scalar store pattern.  
Store sectors fall from 4.19M to 2.10M as each output element becomes half the size.

Global loads and stores retain full sector utilization:

```text
Average bytes / global-load sector    32 / 32
Average bytes / global-store sector   32 / 32
Excessive global sectors                    0
```

Shared-memory work also decreases:

| Metric | Step 06 | Step 07 |
| --- | ---: | ---: |
| Dynamic shared memory / block | 18,432 B | 9,216 B |
| Shared-load requests | 6.44B | 5.37B |
| Shared-load wavefronts | 10.74B | 7.52B |
| Shared-store requests | 268.70M | 134.35M |

Shared-load requests decrease by 16.7% and wavefronts by 30.0%.

The reduction differs across access paths:  
vectorized Q/K reads carry more values per instruction, while V reads during $PV$ remain scalar.

## Lower MIO pressure and better scheduling

MIO-throttle stalls fall from 6.77 to 3.69 cycles per issued instruction,  
while total warp cycles per issued instruction fall from 15.96 to 11.89.

Active warps per scheduler remain at 7.97, but eligible warps increase from 1.51 to 2.26.  
Issue-active cycles consequently rise from 50.0% to 67.1%.

More of the resident warps are ready to issue, improving scheduler efficiency without an occupancy increase.

## Resource footprint and occupancy

| Metric | Step 06 | Step 07 |
| --- | ---: | ---: |
| Registers / thread | 64 | 52 |
| Allocated registers / thread | 64 | 56 |
| Block limit — registers | 4 | 4 |
| Block limit — shared memory | 5 | 10 |
| Block limit — warps | 6 | 6 |
| Theoretical occupancy | 66.7% | 66.7% |
| Achieved occupancy | 66.5% | 66.5% |

The smaller shared-memory footprint raises the shared-memory block limit,  
but registers still restrict residency to four blocks per SM.

Register usage decreases in this build, without crossing the next residency boundary.  
This is specific to the compiled kernel; FP16 storage does not inherently guarantee fewer registers.

## Remaining bottlenecks

The shared-load conflict count remains negligible, while shared-store conflicts persist:

| Metric | Step 06 | Step 07 |
| --- | ---: | ---: |
| Shared-load bank conflicts | 0.25M | 0.12M |
| Shared-store bank conflicts | 205.12M | 83.31M |
| Shared-store wavefronts / request | 4.76 | 4.62 |

Total shared-store conflicts fall by 59.4%, alongside a 50% reduction in store requests.  
The wavefronts-per-request ratio decreases only slightly, so the store layout still carries a serialization cost.

MIO throttle remains the largest stall reason.  
High L1/TEX throughput (94.3%) and low DRAM throughput (0.31%) indicate continued pressure on the on-chip memory path.

Arithmetic also remains scalar FP32:

```text
FMA-pipe utilization       32.8%
Tensor-pipe utilization     0.0%
```

The reported 94.3% SM throughput therefore does not imply saturated FP32 arithmetic.

## Conclusion

Step 07 halves the storage footprint and global-load traffic,  
reducing shared-memory work and MIO stalls.

Scheduler efficiency improves while occupancy remains unchanged.  
The remaining on-chip memory pressure and scalar FP32 matrix operations motivate further optimization.

Step 08 introduces WMMA for $QK^\top$, beginning the transition to Tensor Core computation.
