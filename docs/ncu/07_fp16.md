# Nsight Compute Analysis — Step 07: FP16 Data Path

This document contains the detailed Nsight Compute analysis for [Step 07: FP16 Data Path](../07_fp16.md).

The goal is to measure how changing Q, K, V, and O storage from FP32 to FP16 affects data movement while retaining FP32 arithmetic for the dot products, online softmax, and output accumulation.

## Profiling setup

Representative workload:

```text
GPU: NVIDIA GeForce RTX 5090
dtype: FP16 storage with FP32 accumulation

B = 8
H = 16
N = 4096
d = 64
```

As in Step 06, the complete attention operation runs inside:

```text
fused_attention_kernel
```

The fused attention algorithm, tile sizes, thread mapping, and swizzled shared-memory access pattern are retained.

Step 07 changes the data path:

```text
FP32 Q/K/V/O storage
        ↓
FP16 Q/K/V/O storage

FP32 dot-product, softmax, and O accumulators remain
```

This step does not use Tensor Cores.

## Overview

| Metric                     | Value |
| -------------------------- | ----: |
| Kernel duration            | 79.30 ms |
| SM Throughput              | 94.3% |
| Memory Throughput          | 94.3% |
| L1/TEX Throughput          | 94.3% |
| L2 Throughput              | 15.6% |
| DRAM Throughput            | 0.31% |
| Theoretical Occupancy      | 66.7% |
| Achieved Occupancy         | 66.5% |
| Eligible warps / scheduler |  2.26 |
| Tensor-pipe utilization    |  0.0% |

The kernel is still limited by the on-chip execution and memory path rather than DRAM bandwidth.

The top-level SM throughput should not be interpreted as 94.3% FP32 arithmetic utilization. 
In this profile, it matches the L1/TEX throughput, while the FMA pipeline reaches 32.8% and the Tensor Core pipeline remains unused.

Compared with the Step 06 profile, FP16 storage reduces the amount of data and the number of memory operations that the kernel must process:

| Metric                            | Step 06 FP32 | Step 07 FP16 |
| --------------------------------- | -----------: | -----------: |
| Kernel duration                   |     88.48 ms |     79.30 ms |
| Dynamic shared memory / block     |     18,432 B |      9,216 B |
| Global-load requests              |      268.70M |      134.35M |
| Global-load sectors               |        4.30B |        2.15B |
| Shared-load requests              |        6.44B |        5.37B |
| Shared-load wavefronts            |       10.74B |        7.52B |
| MIO-throttle stall / issued inst. |  6.77 cycles |  3.69 cycles |
| Warp cycles / issued inst.        | 15.96 cycles | 11.89 cycles |
| Eligible warps / scheduler        |         1.51 |         2.26 |
| Issue-active cycles               |        50.0% |        67.1% |

The NCU-measured duration decreases by approximately 10.4% while the memory path remains near its throughput ceiling.

This is possible because throughput is a rate, not a measure of total work:  
Step 07 completes less memory work in less time while keeping the L1/TEX path similarly busy.

The project's benchmark table treats Step 07 as the start of the FP16 track and therefore leaves `vs. prev.`  
blank across the Step 06 FP32 to Step 07 FP16 boundary.  
The duration comparison above is a profiler-side comparison of the same shape, not a same-dtype benchmark speedup claim.

---

## Half-sized global-memory data path

The 16-byte vector access width is retained, but each access now carries twice as many tensor elements:

```text
Step 06    16 bytes = 4 FP32 values
Step 07    16 bytes = 8 FP16 values
```

As a result, the global-load request and sector counts both fall exactly in half:

```text
Global-load requests

Step 06    268,697,600
Step 07    134,348,800

Global-load sectors

Step 06    4,299,161,600
Step 07    2,149,580,800
```

The output still requires the same number of logical stores, so the global-store request count remains unchanged:

```text
Global-store requests

Step 06      1,048,576
Step 07      1,048,576
```

However, each stored element is now half the size, and the number of store sectors falls from 4,194,304 to 2,097,152.

Nsight Compute reports:

```text
Average bytes / global-load sector    32 / 32
Average bytes / global-store sector   32 / 32
Excessive global sectors                    0
```

The FP16 kernel therefore preserves fully utilized global-memory sectors.

The improvement comes from moving fewer bytes and issuing fewer vector-load requests, not from repairing an uncoalesced access pattern.

---

## Reduced shared-memory footprint and traffic

Changing the Q, K, and V tiles from FP32 to FP16 halves the dynamic shared-memory footprint:

```text
Step 06    18,432 bytes / block
Step 07     9,216 bytes / block
```

The aggregate shared-load request count falls by 16.7%:

```text
Step 06    6,442,450,944
Step 07    5,368,709,120
```

The corresponding shared-load wavefront count falls by 30.0%:

```text
Step 06    10,737,666,083
Step 07     7,516,308,180
```

Shared-store requests fall exactly in half, from 268,697,600 to 134,348,800.

The shared-load count does not fall by a full 2× because FP16 storage does not halve every instruction in the kernel.  
The logical attention computation and FP32 accumulation dataflow remain unchanged, and only the storage-facing portions benefit directly from the narrower representation.

The result is nevertheless a substantial reduction in work presented to the shared-memory and MIO paths.

---

## Lower MIO pressure and better scheduler efficiency

MIO throttle remains the largest warp-stall reason, but it falls from 6.77 to 3.69 cycles per issued instruction:

```text
MIO-throttle stall / issued instruction

Step 06    6.77 cycles
Step 07    3.69 cycles
```

The overall warp latency also falls:

```text
Warp cycles / issued instruction

Step 06    15.96 cycles
Step 07    11.89 cycles
```

In Step 07, MIO throttle accounts for approximately 31.1% of the average cycles between issued instructions, compared with approximately 42.4% in Step 06.

The number of active warps is nearly unchanged:

```text
Active warps / scheduler

Step 06    7.97
Step 07    7.97
```

However, more of those resident warps are ready to issue:

```text
Eligible warps / scheduler

Step 06    1.51
Step 07    2.26
```

Issue-active cycles consequently rise from 50.0% to 67.1%.

FP16 storage therefore improves scheduler efficiency without increasing occupancy:  
each resident warp encounters less memory-instruction pressure and becomes eligible sooner.

---

## Resource footprint and occupancy

The compiled Step 07 kernel uses fewer registers:

```text
Registers / thread

Step 06    64
Step 07    52
```

The hardware allocation is:

```text
Allocated registers / thread

Step 06    64
Step 07    56
```

Nsight Compute reports the following residency limits:

```text
                              Step 06    Step 07
Block limit — registers             4          4
Block limit — shared memory         5         10
Block limit — warps                 6          6
```

The halved shared-memory footprint doubles the shared-memory block limit, but registers still permit only four resident blocks.

With eight warps per block:

```text
4 blocks
× 8 warps / block
= 32 warps / SM
```

This produces 66.7% theoretical occupancy, and achieved occupancy remains approximately 66.5% in both steps.

The lower register count is a compiler and code-generation result of this implementation.  
FP16 storage does not inherently guarantee lower register usage, and here the reduction does not cross the next residency boundary.

---

## FP16 storage is not Tensor Core computation

Step 07 stores Q, K, V, and O in FP16, but the numerical work is still performed with FP32 scalar arithmetic:

```text
QK^T dot-product accumulation    FP32
online-softmax state             FP32
P × V accumulation               FP32
final output storage             FP16
```

Nsight Compute confirms:

```text
Tensor-pipe utilization     0.0%
FMA-pipe utilization       32.8%
Achieved FP32 roofline       8%
```

The FMA pipeline is better utilized than in Step 06 because the reduced memory work allows arithmetic instructions to issue more frequently.  
It is not saturated, and no Tensor Core instructions are executed.

The profiler-side duration reduction should therefore be attributed to the narrower data path and lower instruction pressure,  
not to higher-throughput FP16 matrix arithmetic.

Step 08 introduces WMMA for the $QK^\top$ computation and begins using Tensor Cores.

---

## Remaining shared-memory store conflicts

The XOR-swizzled shared-load path remains effective.

Nsight Compute reports only:

```text
Shared-load bank conflicts

Step 06       247,843
Step 07       115,412
```

The remaining warning is on shared stores:

```text
Shared-store requests          134,348,800
Shared-store wavefronts        620,700,396
Shared-store bank conflicts     83,305,196
Average shared-store conflict      4.6-way
```

The store-conflict count is 59.4% lower than Step 06's 205,115,397 conflicts, largely alongside the halved shared-store request count.

Nsight Compute reports that these conflicts represent approximately 13.4% of the shared-store wavefronts.

This is a residual shared-memory-layout cost, 
but it is much smaller than the 30.07 billion shared-load conflicts removed by the Step 06 swizzle.

MIO throttle remains the largest warp-stall reason, although it cannot be attributed entirely to these store conflicts:  
the MIO path also handles other shared-memory operations, special math instructions, and dynamic branches.

---

## DRAM is still not the bottleneck

The memory hierarchy shows:

```text
L1/TEX Throughput    94.3%
L2 Throughput        15.6%
L2 hit rate          99.4%
DRAM Throughput      0.31%
```

The measured DRAM traffic is:

```text
DRAM reads     368.8 MB
DRAM writes     60.7 MB
```

The very high L2 hit rate and negligible DRAM throughput show that repeated tile accesses remain on-chip.

Step 07 is therefore not DRAM-bandwidth-bound.  
Its limiting path remains inside the SM, where L1/TEX and MIO handle the shared-memory-heavy scalar attention loop.

---

## Overall

Step 07 narrows the storage data path without changing the fused attention algorithm or its FP32 accumulation strategy:

```text
FP32 storage
    ↓
FP16 Q/K/V/O storage
    ↓
twice as many values per 16-byte vector load
    ↓
half as many global-load requests and sectors
    ↓
smaller shared-memory footprint and fewer shared transactions
    ↓
lower MIO-throttle stalls
    ↓
more eligible warps and higher issue efficiency
```

In the NCU profiles, kernel duration falls from 88.48 ms to 79.30 ms while achieved occupancy remains unchanged at approximately 66.5%.

The profile also makes the next limitation clear:

```text
FP16 storage
    ↓
FP32 scalar multiply-add loops remain
    ↓
Tensor-pipe utilization stays at 0%
```

Step 08 addresses this arithmetic path by replacing the scalar $QK^\top$ loop with WMMA Tensor Core operations.
